How I Fixed an ownCloud Infinite Scale Login Error Caused by an Expired LDAP Certificate

Nov 21 2026-11-21T16:00:00+05:30 by Injamul Mohammad Mollah
9 min

I recently ran into a frustrating issue with my ownCloud Infinite Scale (oCIS) setup. I could no longer log in, even though I was using the correct credentials. At first, it looked like an authentication problem, but the container logs pointed somewhere else: the TLS certificate used by the built-in Identity Management (IDM) service had expired.

If you’re seeing errors such as x509: certificate has expired or is not yet valid or tls: bad certificate when logging in to oCIS, you may be dealing with the same issue.

In this post, I’ll walk through what I found, how I fixed it, and—most importantly—what you should avoid deleting while troubleshooting.

A quick warning before we start: The fix below is for installations using the built-in IDM service with automatically generated LDAP certificates. If you’ve configured your own certificates or use an external LDAP server, don’t delete certificate files based on this guide. Renew the certificate through the system that manages it.

Finding the actual cause

Rather than resetting passwords or changing user settings, I started by checking the ownCloud container logs.

The important part of the log was this:

1
2
3
4
5

ldap identifier backend logon connect error: LDAP Result Code 200 "Network Error":
tls: failed to verify certificate: x509: certificate has expired or is not yet valid:
current time 2026-11-21T12:06:42Z is after 2026-11-21T11:10:49Z

service=idm error="remote error: tls: bad certificate"

That made the problem pretty clear. The LDAP identifier backend was trying to connect to IDM over TLS, but the certificate it received had already expired. The connection failed certificate verification, and the login process couldn’t complete.

So, in this case, the password wasn’t the problem. The certificate was.

If you want to search your own logs for similar messages, try:

1
2

docker logs --since 15m <ocis-container-name> 2>&1 \
  | grep -Ei 'ldap|certificate|identifier|tls|error'

Replace <ocis-container-name> with the name of your ownCloud container.

Where does ownCloud store the IDM certificate?

With the default built-in IDM setup, the LDAP certificate and its private key are stored in the idm directory inside the oCIS data directory.

In my setup, the directory was:

1

/mnt/nfs/media/owncloud-ocis/idm

When I checked its contents, I found:

1
2
3

ldap.crt
ldap.key
ocis.boltdb

Here’s what those files are for:

File What it contains ————— ————————————————– ldap.crt The LDAP TLS certificate ldap.key The private key associated with that certificate ocis.boltdb The persistent IDM database

The important thing to remember is that the certificate files and the IDM database are not the same thing. We only need to deal with the expired certificate and its matching key—not the database.

Your directory may be somewhere else. It depends on your Docker volume mappings and the OCIS_BASE_DATA_PATH setting.

If you aren’t sure which host directory is mounted into the container, run:

1
2

docker inspect <ocis-container-name> \
  --format ''

It’s also worth checking your Compose file for these environment variables:

1
2
3

OCIS_BASE_DATA_PATH
IDM_LDAPS_CERT
IDM_LDAPS_KEY

The last two matter because they may indicate that your deployment uses custom certificate files rather than the automatically generated ones.

Before changing the files

A quick precaution: make sure you’re actually using the built-in IDM and that ldap.crt and ldap.key are the automatically generated files.

If IDM_LDAPS_CERT or IDM_LDAPS_KEY points to certificates you’ve supplied yourself, stop here and renew those certificates instead. The steps below are not intended for custom certificates or external LDAP deployments.

Also, make sure you’ve identified the correct data directory and have a backup before making changes.

Fixing the expired LDAP certificate

Once you’ve confirmed that the files belong to the built-in IDM, the recovery is fairly straightforward.

I’ll use my data directory as the example. Change the path and container name to match your installation.

1. Stop the ownCloud container

First, stop oCIS so it isn’t using the IDM files while we’re changing them:

1

docker stop <ocis-container-name>

For example, my container is named owncloud-ocis, so the command would be:

1

docker stop owncloud-ocis

2. Back up the IDM directory

Before removing anything, I recommend making a copy of the complete IDM directory. It contains persistent data, so it’s worth taking this extra step.

1
2

cd /mnt/nfs/media/owncloud-ocis
sudo cp -a idm "idm.backup-$(date +%F-%H%M)"

This creates a timestamped backup alongside the original idm directory.

Don’t skip this step. Make sure the backup was created successfully before continuing.

3. Remove the expired certificate and its key

For the default built-in IDM setup, remove just these two files:

1

sudo rm -f idm/ldap.crt idm/ldap.key

That’s it. Do not remove ocis.boltdb, and do not delete the entire idm directory.

The database needs to stay in place. Deleting it is unnecessary for this certificate fix and could cause loss of persistent IDM data.

4. Start ownCloud again

Now start the container:

1

docker start <ocis-container-name>

If you’re managing oCIS with Docker Compose, use the relevant service name instead:

1

docker compose up -d <ocis-service-name>

With the default built-in IDM configuration, oCIS should recreate the missing LDAP certificate and key during startup.

Check that the fix worked

I wouldn’t stop at seeing the container running. It’s better to confirm that the certificate was actually recreated and that it is valid.

Check that the files exist

1
2

ls -l /mnt/nfs/media/owncloud-ocis/idm/ldap.crt \
      /mnt/nfs/media/owncloud-ocis/idm/ldap.key

You should see both files. If your data directory is different, update the paths accordingly.

Check the certificate dates

OpenSSL can show when the new certificate becomes valid and when it expires:

1
2
3

openssl x509 \
  -in /mnt/nfs/media/owncloud-ocis/idm/ldap.crt \
  -noout -dates

Look at notBefore and notAfter. Make sure the current system time is within that validity period.

Check the container logs

Next, look at the recent logs:

1
2

docker logs --since 5m <ocis-container-name> 2>&1 \
  | grep -Ei 'ldap|certificate|identifier|tls|error'

The previous certificate-expiration and tls: bad certificate errors should no longer appear.

Finally, try logging in to ownCloud again. If the certificate has been regenerated and the IDM service starts correctly, the original login issue should be resolved.

If you still can’t log in, check the latest logs again. There may be another issue to investigate, but at least you’ll know whether the certificate error is gone.

What if it still doesn’t work?

If the same error keeps appearing, don’t repeat the deletion blindly. Check a few things first:

  • The files weren’t recreated: Check the oCIS startup logs, the configured OCIS_BASE_DATA_PATH, and whether the container can write to the IDM directory.
  • The old certificate is still being used: Your service may be reading a certificate from a different location. Check IDM_LDAPS_CERT and IDM_LDAPS_KEY in your Compose configuration.
  • The data directory is on a mount: If you’re storing oCIS data on NFS or another mounted filesystem, make sure that mount is available and accessible to the container.
  • You’re using custom certificates: Renew them through the system that issued or manages them. Don’t remove them using the commands in this post.
  • The error has changed: If the TLS error is gone but login still fails, investigate the new authentication error separately.

Are Collabora errors part of the same problem?

While checking my logs, I also noticed a couple of Collabora messages:

1
2

unshare failed: Operation not permitted
coolmount: Operation not permitted

They looked worrying at first, but they were separate from the IDM certificate issue. Collabora also reported that it was ready to accept connections on port 9980.

If you see similar messages, don’t assume they’re the reason oCIS login is failing. Troubleshoot Collabora separately unless the logs show a direct connection to the authentication problem.

A few things worth doing to avoid this later

Certificate problems are easy to overlook because everything can work normally until the expiry date arrives. A few simple checks can save you from a surprise login outage:

  • Keep an eye on certificate expiry. Check the notAfter date periodically and set up an alert before it expires.
  • Back up the IDM directory. Include ocis.boltdb in your regular ownCloud backup routine.
  • Know where your certificates come from. Document whether you’re using automatically generated IDM certificates or custom ones.
  • Check your storage mounts. If your oCIS data lives on NFS, make sure the mount is available before starting the container.
  • Keep your deployment details handy. Record the container name, Compose service name, volume mappings, and data directory.

Final thoughts

In my case, the login failure turned out to be an expired LDAP TLS certificate—not a bad password or a broken user account. The log message x509: certificate has expired or is not yet valid was the clue that led me to the IDM directory.

For the default built-in IDM setup, removing the expired, automatically generated ldap.crt and ldap.key after taking a backup allowed oCIS to recreate them on startup.

The most important part of this fix is knowing what not to delete: keep ocis.boltdb and leave the rest of the IDM directory alone. And if you’re using custom certificates, renew those rather than following the certificate-removal steps.

Hopefully, this saves someone else a bit of debugging time the next time an ownCloud Infinite Scale login suddenly stops working.

Frequently asked questions

Can an expired LDAP certificate stop me from logging in to ownCloud Infinite Scale?

Yes. If the LDAP identifier backend can’t establish a trusted TLS connection to the built-in IDM service, authentication can fail even when your username and password are correct.

Is this a password issue?

Not when the logs show the certificate-expiration error described above. In that situation, the LDAP TLS connection is failing before the login process can complete.

Can I delete ldap.crt and ldap.key?

Only if you’ve confirmed they’re the automatically generated certificates used by the built-in IDM. Back up the IDM directory first. Don’t use this method for custom certificates or external LDAP services.

Should I delete ocis.boltdb too?

No. Keep it. It is the persistent IDM database and is not part of the certificate files being regenerated.

How can I check the LDAP certificate’s expiry date?

Run:

1

openssl x509 -in /path/to/idm/ldap.crt -noout -dates

The notAfter value shows when the certificate expires.
